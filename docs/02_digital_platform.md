# デジタル共通窓口・データ基盤・API設計案

> **本書の位置づけ**：省庁横断の「デジタル共通窓口」と、防災×福祉×都市計画のデータ基盤を設計するための叩き台（ドラフト v0.1）です。
> 組織を新設するのではなく、**手続きとデータをデジタルで横串に通し、進捗を可視化する**ことで縦割りを越えることを狙います。
>
> 関連 Issue：[#3 【データ】3D都市モデル（PLATEAU）とハザードマップを重ね合わせる際、避難ルート計算に必要なデータ項目は？](https://github.com/neuvecom/japan-adaptation-vision/issues/3)／[#2 【行政/制度】一括申請のための法的障壁](https://github.com/neuvecom/japan-adaptation-vision/issues/2)

## 📌 1. 解決したい課題

| 現状の課題 | 起きていること | 本基盤での対応 |
|---|---|---|
| 申請窓口の分断 | 国交省（住宅・都市）、厚労省（介護・福祉）、内閣府（防災）、デジタル庁（システム）へ個別に申請・協議 | **ワンストップ申請**：1つの窓口・1つの申請データで複数制度へ同時申請 |
| 審査状況の不透明さ | どの省庁で止まっているか申請者に見えず、後回し・たらい回しが起きやすい | **進捗の可視化**：各審査のステータスと滞留日数を申請者・全省庁に公開 |
| データのサイロ化 | 3D都市モデル、ハザード、介護施設、避難所のデータが別々に管理 | **データ連携基盤**：共通IDでレイヤー統合し、計画・審査・避難に使い回す |
| 被災時の行政停止 | 本庁舎・サーバーの被災で申請・決裁・予算執行が止まる | **副都心バックアップ**：データと手続き機能を複数拠点で冗長化 |

## 🏛 2. 全体アーキテクチャ

```text
            ┌───────────────────────────────────────┐
 申請者 ─→  │ ① 共通フロント（Web窓口）                            │
（自治体・   │    ・申請フォーム（共通項目＋制度別の追加項目）        │
 民間事業者）│    ・進捗ダッシュボード（全制度のステータスを一画面で）│
            └───────────────┬───────────────────────┘
                            │ 申請API / ステータスAPI
            ┌───────────────┴───────────────────────┐
            │ ② 手続き連携ハブ（ワークフロー・エンジン）              │
            │    ・共通申請データを各制度の様式へ変換・振り分け        │
            │    ・各省庁の審査ステータスを集約、滞留アラート          │
            └──┬──────────┬──────────┬──────────┬───┘
               │          │          │          │
          国交省系     厚労省系     内閣府系    自治体
          審査システム  審査システム  （防災）    （都市計画・福祉・防災部局）
            ┌───────────────────────────────────────┐
            │ ③ データ連携基盤（空間データ・拠点データ）              │
            │    PLATEAU／ハザード／介護・福祉施設／避難所／拠点ステータス│
            └───────────────────────────────────────┘
            ④ バックアップ拠点（副都心・地方拠点で多重化）
```

* **① 共通フロント**：申請者が触る唯一の画面。事業者認証は GビズID、自治体職員は既存の自治体認証基盤との連携を想定します。
* **② 手続き連携ハブ**：既存の各省庁システムを置き換えるのではなく、**「上にかぶせて束ねる」** 構成とします。各省庁側の改修は「ステータスを返すAPI」の追加を最小要件とします。
* **③ データ連携基盤**：計画段階（どこに拠点が必要か）、審査段階（立地・仕様の確認）、災害時（避難・受入れ状況）で同じデータを使い回します。
* **④ バックアップ**：[README](../README.md) の「広域防災・副都心構想との連動」に対応し、首都直下地震等で本拠点が停止しても申請・決裁を継続できるようにします。

## 📝 3. ワンストップ申請の設計

### 3-1. 申請データの構成
申請データを「全制度で共通の部分」と「制度ごとの追加部分」に分け、**共通部分は一度入力すれば全制度に再利用**します。

| 区分 | 主な項目 | 用途 |
|---|---|---|
| 事業者情報 | 法人番号、代表者、GビズID、連絡先 | 全制度共通 |
| 事業計画 | 事業名、所在地（地番・緯度経度・不動産ID）、事業期間、総事業費 | 全制度共通 |
| 建物情報 | 構造、階数、延床面積、戸数、設計浸水深、設備配置階 | 住宅・建築系制度、防災系制度 |
| 福祉機能 | サービス種別、定員、併設事業所、人員配置 | 介護・福祉系制度 |
| 防災機能 | 受入れ可能人数、備蓄量、非常用電源の運転時間、防災協定の有無 | 防災系制度、自治体指定 |
| 経費区分 | 経費項目ごとの金額と、どの制度に計上するか（按分表） | 重複補助の防止、会計検査対応 |

### 3-2. 経費按分表（重複補助の防止）
複数制度を組み合わせると「同じ経費に二重に補助が出ていないか」が最大の審査論点になります。申請時に経費項目 × 制度のマトリクスを機械可読な形で提出し、ハブ側で自動チェックします。

```yaml
# 経費按分表の例（仮のスキーマ）
cost_allocation:
  - item: 受変電設備の高所設置
    amount: 40000000
    allocations:
      - program: housing_subsidy      # 住宅系補助
        ratio: 0.5
      - program: disaster_prevention  # 防災系補助
        ratio: 0.5
  - item: デイサービス室の整備
    amount: 60000000
    allocations:
      - program: care_facility_grant  # 介護・福祉系交付金
        ratio: 1.0
```

## 📊 4. 進捗の可視化（ステータス・トラッキング）

### 4-1. 共通ステータス定義
各省庁・各制度の審査状態を、次の共通ステータスに対応づけて表示します。

| ステータス | 意味 |
|---|---|
| `submitted` | 受付済み（申請データの形式チェック完了） |
| `in_review` | 審査中 |
| `info_requested` | 申請者へ追加資料を求めている（ボールは申請者側） |
| `pending_other` | 他制度・他省庁の審査結果待ち（依存関係を明示） |
| `approved` / `conditionally_approved` | 採択・内定（条件付き） |
| `rejected` | 不採択（理由の記載を必須とする） |
| `withdrawn` | 取下げ |

### 4-2. 可視化のルール（案）
* **滞留日数の表示**：各ステータスの経過日数を表示し、制度ごとに定めた「標準処理期間」を超えたら申請者と所管部署の双方に通知します。
* **ボールの所在の明示**：「いま誰の対応待ちか」（申請者／A省／B省／自治体）を常に1つに特定して表示します。
* **依存関係の明示**：「B省の審査はA省の結果待ち」といった依存を `pending_other` と依存先IDで記録し、循環待ち（お見合い）を検知します。
* **統計の公開**：個別案件は非公開としつつ、制度別の平均処理日数・滞留件数はオープンデータとして定期公開します。これが「握りつぶし・後回し」を抑止する仕組みの中核です。

## 🗺 5. データ連携基盤とデータ項目

### 5-1. レイヤー構成

| レイヤー | 主なデータソース | 主な用途 |
|---|---|---|
| 3D都市モデル | 国土交通省 PLATEAU（CityGML） | 建物高さ・形状、地盤高、道路形状 |
| ハザード | 洪水・内水・高潮の浸水想定区域、土砂災害警戒区域、重ねるハザードマップ | 立地評価、設計浸水深の設定、避難ルート計算 |
| 福祉・医療 | 介護サービス情報公表システム、医療機関情報 | 拠点候補の抽出、要支援者の分布把握 |
| 避難 | 指定緊急避難場所・指定避難所データ、防災協定施設 | 受入れ先の検索・誘導 |
| 動的データ | 河川水位、雨量レーダー・降雨予測、冠水センサー | 避難判断、ルートの動的な更新 |
| 拠点ステータス | 各「防災複合型・高齢者住宅」から送信 | 受入れ可能人数、電源・給水状態のリアルタイム共有 |

### 5-2. 避難ルート計算に必要なデータ項目（Issue #3 の整理）

**① 道路・歩道（ネットワークのリンク属性）**

| 項目 | 型 | 説明 |
|---|---|---|
| `width_m` | 数値 | 有効歩道幅（車椅子がすれ違えるか：目安 1.5m 以上） |
| `step_height_cm` | 数値 | 段差の高さ（2cm を超える段差は車椅子通行困難として扱う） |
| `slope_percent` | 数値 | 縦断勾配（5% を超える区間は介助が必要として扱う） |
| `ground_elevation_m` | 数値 | 路面標高（冠水深の算出に使用） |
| `is_underpass` | 真偽 | アンダーパス・地下道など凹部か（冠水時は通行不可として除外） |
| `drain_adjacent` | 真偽 | 側溝・水路に隣接するか（冠水時の転落危険） |
| `lighting` | 真偽 | 夜間照明の有無 |

**② 建物（拠点・避難先の属性）**

| 項目 | 型 | 説明 |
|---|---|---|
| `entrance_elevation_m` | 数値 | 出入口の標高 |
| `flood_barrier` | 真偽 | 止水板・防水扉の有無 |
| `design_flood_depth_m` | 数値 | 設計浸水深（[01_urban_architecture.md](./01_urban_architecture.md) 参照） |
| `lowest_habitable_floor` | 整数 | 浸水時に使える最下階 |
| `elevator_backup_power` | 真偽 | 非常用電源接続エレベーターの有無 |
| `is_piloti` | 真偽 | ピロティ構造か |
| `capacity_evacuees` | 整数 | 地域避難者の受入れ上限人数 |
| `accessible_24h` | 真偽 | 24時間アクセス可能な避難動線の有無 |

**③ 動的データ（リアルタイム／予測）**

| 項目 | 説明 |
|---|---|
| 河川水位・内水位 | 水位計・冠水センサーの観測値（5〜10分間隔） |
| 降雨強度予測 | 雨量レーダーの短時間予測（〜1時間先） |
| 予測冠水深 | 降雨予測と地形（PLATEAU 地盤高）から算出したリンクごとの予測冠水深 |
| 通行止め情報 | 道路管理者・警察からの規制情報 |

**ルート計算の基本ルール（案）**
* 予測冠水深が **10cm 以上** のリンクは要支援者ルートから除外、**30cm 以上** のリンクは全ルートから除外します（歩行困難の目安、要検証）。
* アンダーパスは降雨強度が一定値を超えた時点で予防的に除外します。
* 利用者の属性（独歩／杖／車椅子／ストレッチャー搬送）ごとに、段差・勾配・幅の閾値を切り替えます。

## 🔌 6. API設計案

REST（JSON）を基本とし、空間データは GeoJSON、3D データは PLATEAU の CityGML／3D Tiles を参照します。以下はエンドポイントの叩き台です。

### 6-1. 申請・ステータス API

| メソッド | パス | 概要 |
|---|---|---|
| `POST` | `/v1/applications` | 共通申請データを登録し、対象制度へ振り分け |
| `GET` | `/v1/applications/{id}` | 申請内容の取得 |
| `GET` | `/v1/applications/{id}/status` | 全制度の審査ステータスを一括取得 |
| `POST` | `/v1/applications/{id}/documents` | 追加資料の提出 |
| `PUT` | `/v1/reviews/{review_id}/status` | （省庁・自治体側）審査ステータスの更新 |
| `GET` | `/v1/stats/processing-time` | 制度別の平均処理日数・滞留件数（オープンデータ） |

```json
// GET /v1/applications/APP-2026-000123/status のレスポンス例
{
  "application_id": "APP-2026-000123",
  "project_name": "〇〇市 防災複合型高齢者住宅整備事業",
  "reviews": [
    {
      "review_id": "RV-001",
      "authority": "国土交通省",
      "program": "housing_subsidy",
      "status": "approved",
      "days_in_status": 0
    },
    {
      "review_id": "RV-002",
      "authority": "厚生労働省",
      "program": "care_facility_grant",
      "status": "in_review",
      "days_in_status": 47,
      "standard_days": 30,
      "overdue": true
    },
    {
      "review_id": "RV-003",
      "authority": "〇〇市 防災課",
      "program": "evacuation_site_designation",
      "status": "pending_other",
      "depends_on": ["RV-002"]
    }
  ],
  "ball_holder": "厚生労働省"
}
```

### 6-2. 拠点ステータス API（災害時）

| メソッド | パス | 概要 |
|---|---|---|
| `POST` | `/v1/sites/{site_id}/status` | 拠点から状態を送信（浸水深、電源、受入れ人数など） |
| `GET` | `/v1/sites?bbox=...&available=true` | 範囲内で受入れ可能な拠点を検索 |
| `GET` | `/v1/routes?from=...&to=...&profile=wheelchair` | 属性別の避難ルートを取得 |

```json
// POST /v1/sites/SITE-0042/status のリクエスト例
{
  "timestamp": "2026-09-24T03:10:00+09:00",
  "flood_depth_m": 0.8,
  "power": { "source": "generator", "fuel_remaining_hours": 58 },
  "water_supply": "available",
  "elevator_operational": 1,
  "occupants": { "residents": 62, "evacuees": 45 },
  "capacity_remaining": 35,
  "needs": ["酸素ボンベ", "簡易トイレ"]
}
```

## 🔐 7. 非機能要件とガバナンス

* **個人情報の保護**：要配慮個人情報（要介護度・病歴等）は、拠点ステータスでは **人数の集計値のみ** を共有します。個人単位の避難行動要支援者名簿との連携は、災害対策基本法に基づく名簿の利用範囲に限定します。
* **可用性**：平時 99.5%、災害時は拠点ステータスAPIを最優先で維持します。クラウド（ガバメントクラウド等）の複数リージョンと副都心のバックアップ拠点で冗長化します。
* **オープン標準**：API仕様は OpenAPI 形式でこのリポジトリに公開し、特定ベンダーに依存しない実装を可能にします。
* **段階的導入**：
  1. **フェーズ1**：進捗の可視化のみ（各省庁はステータスを入力するだけ。既存の申請手続きは変えない）
  2. **フェーズ2**：共通申請データによる一括申請（制度別様式への自動変換）
  3. **フェーズ3**：データ連携基盤・拠点ステータスAPIと接続し、計画から災害対応まで一気通貫
